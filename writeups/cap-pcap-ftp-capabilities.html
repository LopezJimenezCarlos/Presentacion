CAP: insecure packet capture exposure, FTP credential reuse and cap_setuid privesc

Intrusión Linux a partir de un panel web con capturas históricas expuestas, recuperación de credenciales FTP en claro y escalada a root mediante cap_setuid en Python.

Versión pública profesional: la contraseña FTP y las flags visibles en las capturas se han saneado antes de publicarlas, pero la cadena técnica se mantiene intacta.

Executive summary

La máquina CAP cae por una cadena corta pero muy pedagógica: primero se identifica un panel web de monitorización accesible en el puerto 80; después se enumeran rutas funcionales del dashboard, incluyendo vistas de red y capturas históricas; una captura antigua permite recuperar credenciales FTP transmitidas en claro; esas credenciales se reutilizan por SSH y, ya dentro del sistema, una capability peligrosa asignada a Python permite elevar privilegios a root.

Attack path

El escaneo inicial revela 21/tcp, 22/tcp y 80/tcp. Gobuster descubre /ip, /netstat y la sección /data. El panel expone información operativa del host y, razonando sobre referencias directas previsibles, se accede a una captura anterior que contiene una sesión FTP con autenticación en claro. La credencial se valida por SSH sobre el usuario nathan y la escalada final se consigue abusando de cap_setuid en /usr/bin/python3.8.

Recruiter signal

Este writeup muestra un tipo de razonamiento valioso en entornos reales: no se depende de un exploit remoto complejo, sino de correlacionar exposición web, fuga de telemetría, análisis de tráfico y hardening deficiente del sistema operativo.

Command notebook

Comandos representativos del laboratorio. Se mantienen los pasos, pero los secretos se omiten en la versión pública.

nmap -sV -sS 10.129.65.25
gobuster dir -u http://10.129.65.25/ -w /usr/share/wordlists/dirb/common.txt -o gobuster_cap.txt

# desde el panel se localiza y descarga una captura histórica (0.pcap)

getcap -r / 2>/dev/null
/usr/bin/python3.8 -c 'import os; os.setuid(0); os.system("/bin/bash")'

Pasos razonados con evidencias

01

Reconocimiento de red y servicios

La validación de conectividad seguida de nmap -sV -sS muestra una superficie pequeña y muy enfocada: vsftpd 3.0.3, OpenSSH 8.2p1 y una aplicación web servida por Gunicorn. La conclusión aquí es que la entrada más prometedora está en la web, pero el FTP puede terminar siendo importante si más adelante aparecen credenciales.

Razonamiento: con solo tres servicios expuestos conviene priorizar la aplicación web y guardar FTP/SSH como posibles pivotes.
02

Perfilado del dashboard y descubrimiento de rutas

La interfaz web presenta un panel de seguridad aparentemente legítimo, con secciones de snapshot, análisis y estado de red. Al complementar la navegación manual con Gobuster aparecen rutas muy reveladoras: /data, /ip y /netstat. Eso sugiere que la aplicación expone información interna del host sin demasiada separación entre frontend y backend.

Razonamiento: cuando un dashboard enseña métricas operativas, las rutas auxiliares suelen filtrar más información de la que aparenta la portada.
03

Fuga directa de configuración de red

La ruta /ip devuelve la salida de la configuración de interfaces del servidor. No es todavía una vía de ejecución, pero sí una confirmación de que el dashboard está renderizando salidas del sistema de forma casi cruda. Ese patrón suele acompañar fallos de control de acceso o referencias inseguras en otras secciones.

Razonamiento: si el panel publica ifconfig, merece la pena probar si también conserva capturas anteriores o salidas de diagnóstico reutilizables.
04

Confirmación de telemetría sensible en /netstat

La sección /netstat enseña conexiones activas, puertos en escucha y sockets Unix. Ver esa salida desde el navegador confirma que la aplicación no solo resume datos, sino que expone artefactos operativos completos. Ese contexto refuerza la hipótesis de que la sección de capturas puede almacenar ficheros accesibles por identificadores previsibles.

Razonamiento: si el mismo panel publica netstat sin filtrar, es razonable buscar referencias históricas reutilizando IDs o capturas previas.
05

Acceso a una captura histórica y análisis de tráfico

Desde la zona de datos del dashboard se localiza una captura previa, 0.pcap. Al abrirla en Wireshark se observa una secuencia HTTP inicial y, poco después, una sesión FTP completa. El paso clave aquí es pensar que un sistema de monitorización suele conservar artefactos anteriores y que un identificador bajo puede pertenecer a una sesión ajena ya registrada.

Razonamiento: el valor real no estaba en la captura más reciente, sino en una anterior accesible mediante referencia directa predecible.
06

Extracción de credenciales FTP en claro

Siguiendo la secuencia TCP del flujo FTP aparecen los comandos USER y PASS junto con la respuesta 230 Login successful. La contraseña real se oculta en la publicación, pero la evidencia deja claro que el servicio transmite credenciales sin cifrado y que son reutilizables fuera de FTP.

Razonamiento: la captura no se usa solo para “ver tráfico”, sino para transformar un hallazgo pasivo en una credencial válida para acceso interactivo.
07

Acceso inicial por SSH con reutilización de credenciales

La credencial recuperada se valida por SSH contra el usuario nathan. Una vez dentro, se confirma el acceso al directorio personal y la presencia de user.txt. Esto demuestra que una exposición aparentemente “solo de monitorización” termina comprometiendo una cuenta real del sistema.

Razonamiento: la prueba importante no era autenticarse por FTP otra vez, sino comprobar reutilización de credenciales en un servicio con shell interactiva.
08

Enumeración local y escalada mediante Linux capabilities

La cuenta nathan no tiene permisos útiles en sudo, así que la enumeración pasa por revisar SUID, capacidades y binarios interesantes. getcap -r / 2>/dev/null revela cap_setuid+eip sobre /usr/bin/python3.8, lo que permite cambiar el UID efectivo a 0 y abrir una shell root de forma directa.

Razonamiento: al agotarse sudo, las capabilities ofrecen una vía de privesc menos ruidosa y muy efectiva cuando recaen sobre intérpretes.

Key findings

The dashboard exposed historical packet captures through predictable references.

El problema principal no era solo “mostrar métricas”, sino publicar artefactos de red anteriores sin control de acceso fuerte ni aislamiento entre usuarios o sesiones.

FTP credentials were transmitted in clear text and reused on SSH.

La reutilización de la misma contraseña entre servicios convirtió una simple captura pasiva en acceso shell real al sistema.

A Python interpreter with cap_setuid enabled trivial root escalation.

Asignar capabilities potentes a intérpretes generalistas elimina gran parte de la separación de privilegios del sistema.

Remediation notes

  • Aplicar control de acceso real sobre capturas, snapshots y rutas operativas del dashboard.
  • Eliminar FTP en texto claro o sustituirlo por SFTP/FTPS con rotación de credenciales.
  • Auditar Linux capabilities y retirar cap_setuid de intérpretes y binarios no esenciales.
